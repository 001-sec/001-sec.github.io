THROTTLEGATE

A rate-limit verification toolkit for web login forms. Confirm that the throttling on your own authentication endpoints behaves the way the configuration says it does.

View on GitHub Quickstart

What it does

Throttling rules drift. A proxy upgrade, a WAF edit or a framework change can quietly alter how limits are counted, most often by hiding the real client address. ThrottleGate measures the limiter itself, per account identifier and per connection origin, so you find out before someone else does.

lab/

Training Lab

A small Flask app with a one-time-code login form. Switch the throttling scope and tune the threshold live, then watch how behavior changes.

GUI Auditor

A desktop tool, no programming required. It sends a rate-capped series of test requests to an endpoint you specify and reports where limits trigger.

The training lab

Learn and demo the concepts locally. The lab keeps all state in memory, depends only on Flask, and exposes a control panel for the rules under test.

  • Attempts per window: set how many failures are allowed before the limiter trips.
  • Scope: key the limit by account identifier, by connection origin, or both.
  • Live switching: change rules while the auditor runs and watch the verdict follow.

The auditor and its reports

Point it at an endpoint you are authorized to assess, confirm authorization, and run. Three phases separate the dimensions a limiter can key on.

PHASE A

Fixed account, direct

The limiter should trip at the configured threshold.

expected: trips
PHASE B

Rotating accounts, same origin

Requests should pass. A per-origin-only limit would block here.

expected: passes
PHASE C

Fixed account, via your gateway

The limiter should trip again, proving it follows the account.

expected: trips

Anything else means effective behavior differs from the intended configuration, and the report explains which dimension is missing. Reports are self-contained HTML with no external assets, plus JSON for pipelines, written locally to auditor/reports/.

Hard caps

Single-threaded, max 10 requests per second, 500 per run. A measuring instrument, not a stress tool.

Authorization gate

Refuses to run without an explicit authorization confirmation, and defaults to a safe mode with minimal traffic.

No credentials needed

Random codes come from a CSPRNG. No valid credential material is required, because the tool reads limiter behavior, not login success.

Quickstart

Everything runs locally against the bundled lab.

# Terminal 1: the lab
cd lab && pip install -r requirements.txt && python app.py

# Terminal 2: the auditor GUI, pointed at the lab
cd auditor && pip install -r requirements.txt && python auditor_gui.py

# Or headless
python engine.py http://127.0.0.1:5000/api/login --yes-i-am-authorized

The defensive guide

Per-account throttling survives origin rotation and does not punish bystanders behind shared addresses. The short version:

  • Count failures, not requests. Successful logins should not drain the budget.
  • Fail closed under pressure. Record throttled attempts too.
  • Answer consistently. Same status, body and timing for unknown account and wrong code.
  • Use a sliding window and return 429 with Retry-After.
  • Layer, don't substitute. Keep a loose per-origin limit, add progressive delay, alert on crossings.
  • Verify, don't assume. Run the auditor after every change that touches the edge.

AUTHORIZED USE ONLY

Built for defenders

Every component of ThrottleGate is built for systems you own or are explicitly authorized to assess, and for learning in the included lab. It sits in the same category as open-source web scanners and load-testing utilities: a verification instrument for defenders.

The auditor refuses to run without an explicit authorization confirmation, caps request rates hard, and defaults to a safe mode that keeps test traffic minimal. If that is not what you are doing, this is not the tool you are looking for.
